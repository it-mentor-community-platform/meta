# Стилистика кода

## Примечание
Тут описанные лишь основные особенности для Java кода (для репозиториев на других языках эти правила действуют лишь 
частично в общих для них моментов), которые стоит поддерживать в коде этого проекта, в остальном стоит ориентироваться 
на [конвенции Java](https://www.oracle.com/java/technologies/javase/codeconventions-introduction.html), и уже реализованные в конкретном репозитории практики.

## Разделение классов

Кроме стандартного разделения на контроллеры, сервисы и репозитории для каждой доменной сущности, стоит также отделять 
обработку публичных эндпоинтов, административных, внутренних и т.д.
- Причины: 
  - Изменения контрактов эндпоинтов, не должны приводить к случайным изменениям поведения на других.
  - Общие сервисы очень быстро увеличиваются в размере, и их в разы сложнее просматривать при ревью, а тем более делать правки в них
  - Желание сократить количество кода выглядящего похоже в одном классе, приводит к постоянному добавлению 
  вспомогательных методов, которые в итоге сложнее тестировать и заставляют каждый раз разбираться со всеми их использованиями 
- Пример: сервисы `CurrentProfileService`, `InternalProfileService` и `AdminProfileService` для обработки действий с профилями
- Анти-пример: контроллер `MentorController` содержащий сразу несколько типов эндпоинтов
---
Репозитории для одной сущности, на разные варианты использования - не разделяем 

## Методы

### Порядок
Публичные методы всегда должны быть размещены в начале класса, приватные всегда в конце

### Разделение
1. Не оставляем методы больше чем на 90 строк кода, или с вложенностью больше 4 табов
2. Стараемся не плодить приватные утилитные методы с одним использованием если это не требует правило 1

### Сигнатуры
Не передаем больше 5 параметров

## Нейминг
Любые отступления от описанного здесь нейминга должны иметь строгие на это причины, которые можно описать в комментарии к PR, 
или наперед обсудить в чате

Язык используемый в файлах с исходным кодом (документация, комментарии, сообщения об ошибках, логи, и т.д.) - **всегда английский**

### Ручные .http тесты
Присутствуют во всех репозиториях с реализованным REST API взаимодействием

#### Директории
- Все файлы ручных тестов должны находится в директории `requests` 
- Директория `requests` всегда должна быть в корне проекта
- Для отдельных групп файлов, если их количество избыточно для удобной навигации, можно выносить в поддиректории
    - Примеры: `requests/admin`, `requests/internal`
#### Название файлов
- Краткое описание названия или смысла эндпоинта для которого создается тест в `kebab-case`
    - Пример: Для эндпоинта `POST /api/users/internal/users`, подходящим тестом будет: `internal-create-user.http`
#### Название тестов
- Каждый тест должен иметь свое название которое состоит из
    - Описания проверяемого случая. Пример: `Validation error: incorect review price provided` 
    - Ожидаемого HTTP кода ответа. Пример: `400`
    - Ожидаемого HTTP статуса ответа. Пример: `Bad Request`
    - Цельный пример: `### Validation error: incorect review price provided - 400 Bad Request`
- Если для срабатывания теста нужны особенные условия, их можно (нужно) описать дополнительным комментарием
    - Пример: `###### Assumed The guaranteed review price with this 'language' and 'projectType' is already exists`

### Объекты для передачи данных (Data Transfer Objects)

#### Тип классов
- Всегда, если есть возможность - иммутабельный тип `record`. Иначе `class`, но должна быть причина зачем этому классу мутабельность

#### Название классов

##### Не используем стандартный суффикс `Dto`, или `DTO` 
Причины: 
  1. Аббревиатура `Data Transfer Object` - содержит избыточное количество уже очевидной для разработчика информации: 
  то что это объект подразумевается из того что в Java все классы автоматически наследуются от `Object`, дополнительно 
  указывать про это в названии каждого класса, нет необходимости. А то что это только промежуточное представление 
  (`Transfer`), можно понять из: оставшейся части `Data`, иммутабельности класса, контекста использования, и в некоторых случаях префикса. 
  2. При этом, в аббревиатуре отсутствует полезная информация про назначение этого класса, где он создается и используется.
  3. Нет единственно правильного подхода как приводить аббревиатуры к множественному числу, суффикс в названиях коллекций содержащих 
  в себе эти классы, все делают разным: `dtos`, `DTOs`, без суффикса, вообще без множественного числа и т.д. В предложенных ниже вариантах,
  такой проблемы, зачастую не возникает: `requests`, `events`, `rows`
  4. Аббревиатуры просто читаются хуже, чем обычные слова

---

- Объекты пришедшие с HTTP запроса, имеют суффикс `Request`
    - Пример: `CreateUserRequest`, `SubmitProjectRequest`, `UpdateProfileDescriptionRequest` 
    - Анти-пример: `UserDTO`, `SubmitProjectRequestDto`, `ProfileDescriptionDto` 
- Объекты отправляемые как HTTP ответ, имеют суффикс `Response`
    - Пример: `CreateUserResponse`, `SubmitProjectResponse`, `UpdateProfileDescriptionResponse`
    - Анти-пример: `CreatedUserDTO`, `SubmitedProjectResponseDto`, `ProfileDescriptionDto`

- _Префиксы на объектов запроса и ответа одного эндпоинта - совпадают. Название файла .http примеров для этого эндпоинта
тоже может содержать его в себе_


- Объекты используемые как сообщение приходящие (отправляемые) из (в) брокер(а), имеют суффикс `Event`
    - Пример: `ReviewSubmitedEvent`, `ProjectSubmitedEvent`, `MontlyReviewBudgetRevisedEvent`
    - Анти-пример: `ReviewSubmitedDTO`, `ProjectSubmitedMessage`, `MontlyReviewBudgetRevised`
- Объекты представляющие собой строку в Google Spreadsheets, имеют суффикс `Row`
  - Пример: `CreatedProjectRow`, `SubmitedReviewRow`
- По мере добавления новых интеграций, этот список стоит обновлять
- В остальных случаях когда ни один из вариантов выше не подходит, и придумать новый подходящий не вышло (например для 
сохранения в кэше может подойти суффикс `Entry`), или класс используется сразу для многих целей, то используем просто суффикс `Data`

#### Название пакетов
Называем также как лежащие в нём классы: `event`, `request`, `response`, `data`


### Сущности
Без особенных суффиксов или префиксов, просто название таблицы в одиночном числе
